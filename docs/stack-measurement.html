Returning frees the stack.
It does not erase the evidence.

Separate from the stack: file payload
monster hulk · 12 bytes, no newline
FTP file/network storage is not drawn as a stack frame. Payload length does not predict stack depth: protocol calls, local variables and interrupts use their own stack space.

A scan sees writes, not every use

Space can be reserved by moving MSP without writing every byte. Untouched frame slots, alignment gaps, or a value equal to the fill pattern can hide use. The deepest changed byte is not the exact historical minimum MSP. The solid live blocks here simplify this: the example assumes writes reach each illustrated depth.

The scan includes all activity since painting: startup, idle, FTP and interrupts. It cannot attribute the trace to FTP alone.

A baseline is not a safety proof

The example leaves 6,624 bytes of unchanged pattern below its trace. That is not a proven safe margin. A tiny successful transfer does not cover other call paths, errors, interrupt nesting or future workloads.

A dump contains all 8,192 reserved bytes for inspection. Dump size is not used stack size. Validate a real measurement path with known-write controls before trusting its results.

Why not paint the whole stack from ordinary C?

Unsafe counterexample — explanation only, not an action to run.

The existing FTP reset-handler disassembly begins with push {r3, lr}: an 8-byte live reset frame at [0x2000FFF8, 0x20010000) before its C body runs. Painting the entire reserved stack from there would erase those saved values. Calling a C painter can add still more live frames.

The proposed safe approach is an FTP-scoped stackless pre-C assembly painter, before any pushes or calls, followed by normal startup. Its final disassembly, bounds, interrupt/fault safety and startup integration still need validation. This page implements none of that firmware procedure.

Educational model only. No firmware, debugger connection, reset, network request or hardware operation is performed. Restart restarts this illustration — not the device.
